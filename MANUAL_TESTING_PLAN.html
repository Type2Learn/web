three-person manual test run

A step-by-step, evidence-led plan for the public website, learner experience, AI-supported learning, assessment, privacy, and educator publishing workflow.

Test windowChoose a 1–2 day window with a stable staging deployment.
ParticipantsTester A · Public & access

Scope is deliberately broader than a visual review. It confirms both what a learner sees and the boundaries that must hold when a feature, model, provider, or integration is unavailable.

1. Rules for the whole test run

Use test data only. Do not upload real learner work, real classroom records, personal health information, production API keys, or voice recordings. Use the disposable test accounts and source material described below.
Before anyone startsRequired checkEvidence / decision
Build identityRecord Git commit, deployment URL, date/time, tester browser, operating system, screen size, and enabled environment flags.Put the information at the top of the shared test sheet. A finding cannot be accepted without the build identifier.
AccountsCreate or confirm six disposable accounts: learner, guest browser profile, teacher, institute owner, platform admin, and a second learner for assignment checks.Never share passwords in screenshots. Delete or reset all test accounts after sign-off.
ProvidersRecord whether Firebase Auth, Firestore/Admin, Gemini, OpenAI fallback, text-to-speech, storage, GitHub backup, and Supabase backup are configured in this environment.Mark an unavailable integration CONDITIONAL, then test the authored fallback instead of treating it as a failure.
Browsers / screensUse at least: Chromium desktop 1440×900, Chromium laptop 1366×768, Firefox or Safari equivalent, Android/iPhone-sized browser, and one keyboard-only pass.Capture any clipping, overlap, unreadable contrast, unexpected scroll lock, focus loss, or motion that ignores settings.
Evidence standardFor every test: mark Pass / Fail / Conditional / Blocked; save one screenshot for visual tests and one request/response or log excerpt for API/provider tests.File defects immediately with test ID, exact action, expected result, actual result, severity, evidence link, and build ID.

Severity and stop rules

SeverityExamplesRelease consequence
P0 — stopPrivate answer key reaches a learner, unauthenticated admin access, raw learner content is uploaded without consent, account takeover, unsafe AI answer disclosure, published course bypasses approval.Stop the run; disable the affected feature and fix before release.
P1 — must fixLearner cannot continue, save or sign in; navigation sends users to the wrong route; key course path fails; Urdu content is unreadable; an accessibility blocker has no alternative.Do not approve release until fixed and retested.
P2 — fix or explicitly acceptIncorrect copy, a non-blocking visual collision, a conditional integration message that is unclear, missing focus indication.Owner records a resolution or time-bound exception.
P3 — polishMinor spacing, wording, or animation polish with no impact on task completion, privacy, or accessibility.Log for the next release.

5. Tester B — learner, support, AI, and assessment

Goal: complete a realistic learner journey with and without optional supports, confirming that no learner is judged by speed and every support remains controllable.

IDStepsExpected resultEvidence
B-01
Guest and learner entry
  1. Open the course as a guest in a fresh profile.
  2. Repeat as a signed-in learner.
  3. Confirm guest data stays browser-local and that signed-in progress has an understandable save state.
Guest can use the intended preview/course features without needing hidden credentials. Sign-in boundary is clear. No guest gets access to privileged teacher/admin routes.Route screenshots and browser-storage/clear-data result; no private data dump.
B-02
Course selection and preferences
  1. Choose Introduction to Neurodivergent Conditions.
  2. Confirm preferences appear only on first course choice; continue, return, and reopen settings from profile.
  3. Exercise Focused, Balanced, Open; Flat, Balanced, Vivid; spacing; encouragement; animation; noise; TTS; mascot; language.
Each choice is visibly distinct and applies immediately where designed. Balanced stays visually plain compared with Vivid. Open uses available width. Preferences remain course-specific and are editable later. Disabled/small-screen mascot explains why it is unavailable.Screenshot matrix: each layout × colour; settings panel; persistence after refresh.
B-03
Background sound and narration
  1. Enable Background noise. Choose white, pink, and brown.
  2. Confirm each begins only after an explicit choice and starts at 0 volume.
  3. Raise/lower volume; navigate, pause/save, refresh, and return.
  4. Enable read-aloud and test start/pause/stop/restart on reading content.
No autoplay or loud start. Selected loop remains stable across ordinary navigation. Volume range obeys its max. Read-aloud has visible state and never starts on its own. If unavailable, it explains the browser limitation.Screen recording of controls; note device/browser audio result.
B-04
Reading and typing loop
  1. Complete a reading section; use “Explain this step,” visual explanation, and skip where allowed.
  2. On the five guided typing sections, type a correct response, a wrong character, backspace, wrap lines, and complete the section.
  3. Try paste, keyboard-only operation, and a long response.
Only reading/preview steps can be skipped. Typing/MCQ cannot be skipped. Guided caret follows the next required character through wrapping; correct text is green, wrong text is red without false red markings. No score or speed pressure is shown.Screenshot of correct/wrong/wrapped typing and each support state.
B-05
Checks, application, pause
  1. Submit correct and incorrect MCQs.
  2. Complete application activity, then pause/save from top bar/logo.
  3. Refresh/reopen and resume.
  4. Confirm “restart” is absent where it has no purpose.
Incorrect feedback is calm, identifies a recovery action, and does not shame/shake/flash. Pause preserves the permitted state. No visible percentage, ranking, answer key, or time requirement appears.Correct/incorrect screenshots and resumed task screenshot.
B-06
Support surfaces
  1. Open “I’m stuck.” Choose every barrier: instruction, too large, difficult words, start, too much on screen, worry about wrong answer.
  2. Use “Talk to AI” from that chooser and open full Course AI.
  3. Send a harmless curriculum question; then cancel/dismiss support and return to task.
Each barrier changes only the current step and gives a bounded relevant support. Full chat remains available. Output does not diagnose, give the complete target answer before an attempt, or become a generic chatbot. Dismissal does not reappear in the same task.One screenshot per barrier; AI request category/result or authored fallback message.
B-07
Adaptive Recall and provider fallbacks
  1. Submit the partial, correct, and incorrect sample responses from section 3.
  2. Trigger Adaptive Recall after a genuine attempt.
  3. Temporarily use an environment with AI disabled/unavailable, if safe, or use a known fallback test route.
Feedback names one demonstrated strength, one missing idea, and one next action in at most two sentences. It never provides a full answer first. Invalid/unavailable provider produces deterministic authored support and allows progress. No raw prompt/key is exposed in the browser.Structured response/fallback evidence with raw learner content redacted.
B-08
Behavioural Learning Partner
  1. Turn on each role: Calm Guide, Learning Partner, Self-Challenge Coach, Visual Co-Explorer.
  2. Try Quiet, Available, Involved; proactive offers on/off; text, voice, both.
  3. Simulate two neutral signals safely: delayed start plus return, reread plus pause, or typing pause plus retry.
  4. Open “Why did this appear?”, dismiss it, and repeat the task.
Roles feel distinct and remain fictional/task-bound. It offers support only after two relevant neutral signals and only one surface per task. It never claims to be a child/person, guilt-trips, diagnoses, or silently changes a setting. Dismissal suppresses that offer for the task. Mobile uses accessible chat instead of loading the mascot.Role screenshots, reason panel, dismissal evidence, mobile result.
B-09
Consent and data panel
  1. Use behaviour/adaptive support with consent off.
  2. Turn adaptive consent on and inspect “What Type2Learn notices.”
  3. Request export, then delete/turn off; refresh and verify the clear state.
Without consent, only local authored support operates; no upload is claimed. With consent, the panel names compact categories—not raw answers, keystrokes, recordings, chat, or psychological labels. Export/delete controls are understandable and effective when Firebase is configured.Before/after screenshots; conditional backend confirmation with UID redacted.
B-10
Assessment and targeted review
  1. Reach a module understanding check.
  2. Answer open questions without a translucent target answer; test text and speech path.
  3. Complete MCQs with correct/incorrect answers.
  4. Force a weak evidence route using partial/incorrect samples; follow review and recheck.
  5. Repeat final course check where available.
One question at a time. Module limits never exceed 4 open + 5 MCQ; final never exceeds 9 open + 12 MCQ. No score, percentage, answer key, or model rationale is shown. A weak result gives a supportive specific review route and bounded recheck; it does not silently fail or trap the learner.Question sequence log, no-score screenshots, review-route screenshot, server run IDs if available.
B-11
Course accessibility and resilience
  1. Run Focused, Balanced, and Open with keyboard only, reduced motion, 200% zoom, and mobile viewport.
  2. Toggle settings popover and click outside/reclick profile to close it.
  3. Disconnect network after page load for a local fallback attempt.
Focused keeps one dominant task; Balanced keeps route visible; Open uses the intended width. Focus is never lost, popup closes appropriately, and no essential content is mascot-only. Offline/provider failure preserves work and gives a calm recoverable message.Keyboard/zoom/mobile screenshots and one offline fallback result.

C-06
Narration and backup gate
  1. Add required narration assets or choose labelled device-TTS fallback according to current policy.
  2. Attempt approval/publication before audio and all backup receipts.
  3. Add/verify Firebase, private GitHub metadata, Supabase package, and downloadable ZIP receipts in the configured test environment.
Publication is blocked until every mandatory gate is satisfied. A missing receipt names the missing system, not a generic error. Backup artifacts do not include credentials, raw source uploads, learner data, or answer keys in learner-accessible locations.Gate-blocked screenshot and masked receipt list.
C-07
Approval, distribution and learner-safe manifest
  1. Approve/publish the safe sample course.
  2. Set distribution: everyone, organisation only, and selected learner.
  3. Check catalogue as each learner/account.
  4. Open the selected course in /course/?courseId=…&version=….
Only assigned learners see/access restricted courses. The selected reviewed course uses the established rich learner UI and its supports. Browser payload contains no private uploads, review notes, answer keys, or MCQ correct options. Checked answers return only safe completion/retry states.Catalogue comparison and a redacted network-response inspection.
C-08
Progress, versioning and deletion
  1. Complete part of version 1; publish a reviewed version 2.
  2. Verify settings/progress are versioned and do not overwrite each other.
  3. Request privacy export and deletion for the test learner.
Course progress/preferences are scoped by course/version. Export covers the learner’s allowed records. Delete removes the documented records and future retrieval returns the expected empty/limited state.Version comparison and deletion confirmation with identifiers masked.
C-09
Health, flags and failure handling
  1. Open the health endpoint and record enabled/disabled capabilities.
  2. Test an unavailable service: Firebase, Gemini, OpenAI fallback, backup target, or storage, in a non-production environment.
  3. Review server response headers and browser console.
Health states accurately report availability. Disabled features fail closed with a useful message; no stack trace, secret, raw provider response, or private path reaches the browser. Core public site remains available when optional AI is unavailable.Redacted health response, error screenshot, browser console export.
C-10
Final release rehearsal
  1. Run one complete source → review → approve → publish → assigned learner → course completion path.
  2. Use Tester B’s learner account for final handoff.
  3. Confirm an admin can view as learner without becoming the learner or changing their data.
One complete theory course becomes usable through the same rich learner experience with existing settings/TTS/completion intact. Human approval and distribution boundaries remain visible at every stage.One chronological evidence folder, release checklist, and Go/No-Go signature.
